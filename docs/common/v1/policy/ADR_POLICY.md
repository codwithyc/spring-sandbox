# ADR_POLICY

## 1. 목적
이 문서는 아키텍처 의사결정(ADR)을 언제, 어떻게 기록할지에 대한 최소 운영 규칙을 정의한다.

## 2. ADR 작성 기준
아래 중 하나에 해당하면 ADR을 작성한다.

- 프로젝트 전반에 영향을 주는 구조/계약 결정
- 한번 결정하면 되돌리기 비용이 큰 기술 선택
- 팀 내 의견 차이가 있었고, 선택 근거를 남겨야 하는 결정

단순 버그 수정, 리팩토링 코드 정리, 네이밍 변경만으로 끝나는 작업은 ADR 대상이 아니다.

## 3. 위치와 파일명
- 위치: `docs/common/v1/adr/`
- 파일명 형식: `ADR-번호-kebab-case.md`
- 예시:
  - `ADR-001-response-envelope.md`
  - `ADR-002-error-code-policy.md`

번호 규칙:
- 3자리 증가값(`001`, `002`, ...)
- 번호는 재사용하지 않는다.

## 4. 상태 관리
모든 ADR은 상태를 명시한다.

- `Proposed`: 제안 단계
- `Accepted`: 채택 완료
- `Superseded`: 다른 ADR로 대체됨
- `Deprecated`: 더 이상 권장하지 않음

## 5. 최소 템플릿
각 ADR에는 아래 항목을 포함한다.

1. 배경(Context)
2. 결정(Decision)
3. 대안(Alternatives)
4. 결과(Consequences)
5. 상태(Status)
6. 관련 문서/코드 링크

## 6. 운영 규칙
- 아키텍처 정책 변경 시 코드 변경 전에 ADR을 먼저 작성하거나 함께 제출한다.
- 기존 결정을 바꿀 때는 기존 ADR을 수정하지 말고 새 ADR을 추가한 뒤 상태를 `Superseded`로 바꾼다.
- ADR 내용은 구현 세부 코드보다 의사결정 근거 중심으로 작성한다.

## 7. 작성 밀도 기준
- 권장 분량: 1~2 페이지
- 한 ADR에는 한 가지 결정만 다룬다.
- 배경 설명보다 결정 근거와 트레이드오프를 우선한다.
