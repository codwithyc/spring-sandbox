# ADR-001: UTC Time Source Policy For Operational Metadata

- Status: Accepted
- Deciders: spring-sandbox maintainers
- Date: 2026-04-10

## 1. Context

본 프로젝트의 공통 응답 구조에는 운영 메타데이터가 포함됩니다.  
특히 `ApiMeta.timestamp`는 사용자 화면 표시용 시간이 아니라, 요청-응답-로그를 연결하고  
문제 발생 시점을 추적하기 위한 시스템 내부 기준 시각입니다.

현재 서비스의 주 사용자는 한국 시간대(KST)에 익숙할 수 있으나,  
서버 내부 기준 시간을 특정 지역 시간대로 고정하면 다음과 같은 문제가 발생할 수 있습니다.

- 외부 시스템과의 연동 시 시각 비교 기준이 일관되지 않을 수 있습니다.
- 로그, 예외, 이벤트, 응답 생성 시각을 상호 비교할 때 해석 비용이 증가할 수 있습니다.
- 테스트 코드에서 현재 시각을 안정적으로 제어하기 어렵습니다.

따라서 이 문서는 "운영 메타데이터에서 어떤 시간 기준과 시간 표현 타입을 사용할 것인가"를 결정합니다.

## 2. Scope

이 ADR은 다음 범위에 적용됩니다.

- 공통 응답 메타데이터의 생성 시각
- 서버 내부에서 추적 목적으로 사용하는 운영 시각 기준
- 공통 컴포넌트에서 주입받아 사용하는 현재 시각 소스

이 ADR은 다음 범위는 직접 다루지 않습니다.

- 사용자 화면에 표시되는 로컬 시간 포맷 정책
- 데이터베이스 컬럼 타입 및 저장 전략
- 외부 API 계약별 개별 시간 포맷 요구사항

## 3. Decision Drivers

다음 기준을 우선순위로 고려했습니다.

- 절대 시점을 모호함 없이 표현할 수 있어야 합니다.
- 로그, 응답, 예외 발생 시각을 동일 기준으로 비교할 수 있어야 합니다.
- 애플리케이션 전반에서 동일한 현재 시각 기준을 재사용할 수 있어야 합니다.
- 테스트에서 현재 시각을 고정하거나 대체할 수 있어야 합니다.

## 4. Decision

운영 메타데이터의 기준 시각은 UTC로 통일합니다.

구체적으로는 다음과 같이 결정합니다.

- 공통 응답 메타데이터의 시각 타입은 `Instant`를 사용합니다.
- 현재 시각은 `Clock` Bean을 통해 주입받습니다.
- 기본 `Clock` 구현은 `Clock.systemUTC()`를 사용합니다.
- 사용자 화면 또는 운영 UI에서 지역 시간대 표현이 필요할 경우, 표시 단계에서 별도로 변환합니다.

즉, 서버 내부의 운영 기준 시간은 UTC로 유지하고,
표시 책임은 소비자 계층(UI, 운영 도구, 외부 클라이언트)에서 담당합니다.

## 5. Rationale

### 5.1 `Instant` 채택 이유

`Instant`는 UTC 기준의 절대 시점을 직접 표현하므로,
시간대 정보가 없는 `LocalDateTime`보다 운영 메타데이터에 적합합니다.

운영 메타데이터의 목적은 "사람이 보기 쉬운 시간"보다
"시스템 간 동일하게 해석되는 시점"을 제공하는 데 있습니다.

### 5.2 `Clock` Bean 채택 이유

현재 시각을 정적 호출로 직접 가져오면 공통 정책을 한 곳에서 통제하기 어렵고,
테스트에서 시각을 고정하기도 불편합니다.

`Clock`을 Bean으로 주입하면 다음 이점이 있습니다.

- 시간 정책을 애플리케이션 구성 수준에서 중앙 관리할 수 있습니다.
- 테스트에서 `fixed Clock` 또는 대체 구현으로 쉽게 교체할 수 있습니다.
- 공통 응답 생성기 등 여러 컴포넌트가 동일한 시각 기준을 공유할 수 있습니다.

## 6. Alternatives Considered

### 6.1 `LocalDateTime`

장점:

- 사람이 읽기에 직관적입니다.

단점:

- 시간대 정보가 없어 절대 시점을 명확하게 표현하지 못합니다.
- 서버, 로그, 외부 시스템 간 시각 비교 시 해석 차이가 생길 수 있습니다.
- 운영 추적용 메타데이터보다는 화면 표시용 표현에 가깝습니다.

결론:

운영 메타데이터의 기준 타입으로는 부적합하다고 판단했습니다.

### 6.2 `OffsetDateTime`

장점:

- 시간대 오프셋을 포함하여 시각을 표현할 수 있습니다.
- API 계약에서 시간대 정보를 명시적으로 드러내고 싶을 때 유용합니다.

단점:

- 본 프로젝트의 운영 메타데이터 목적에는 `Instant`보다 표현이 무겁습니다.
- 기준 시간이 이미 UTC로 고정된 상황에서는 추가 오프셋 표현의 실익이 크지 않습니다.

결론:

운영 메타데이터의 내부 표준으로는 `Instant`가 더 단순하고 명확하다고 판단했습니다.

## 7. Consequences

이 결정의 결과는 다음과 같습니다.

- 응답 메타데이터의 `timestamp`는 UTC 기준 절대 시점으로 기록됩니다.
- KST 등 특정 지역 시각 표시는 서버 내부 정책이 아니라 표시 계층의 책임이 됩니다.
- 공통 응답 생성 컴포넌트는 반드시 주입된 `Clock`을 사용해야 합니다.
- 테스트에서는 시간 의존 로직을 더 예측 가능하게 검증할 수 있습니다.

추가로 주의할 점은 다음과 같습니다.

- 사용자가 보는 시각과 시스템 내부 시각은 분리해서 생각해야 합니다.
- 향후 DB 저장 시간 정책이나 외부 API 시간 계약은 별도의 ADR 또는 정책 문서에서 다루는 것이 바람직합니다.

## 8. Implementation Notes

현재 구현 연결점은 다음과 같습니다.

- `TimeConfig`는 기본 시간 소스로 `Clock.systemUTC()`를 제공합니다.
- `ApiEnvelopes`는 주입받은 `Clock`으로 응답 메타데이터 시각을 생성합니다.
- `ApiMeta.timestamp`는 `Instant` 타입으로 표현됩니다.

이 정책을 따르는 신규 코드에서는 `Instant.now()`를 직접 호출하기보다,
가능한 한 주입된 `Clock`을 사용해야 합니다.
